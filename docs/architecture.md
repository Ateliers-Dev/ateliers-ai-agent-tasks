# 全体構成と運用方針

## ドキュメントの配置

- `docs/<project>/` に、プロジェクトの概要、共有方針、関連資料への参照など、AI サービス間で共有する情報を置く。
- `docs/<project>/<provider>/` に、AI サービス固有の補足や参照先を置く。共通情報はプロジェクト直下の文書へリンクする。
- アプリ本体の詳細設計は開発リポジトリで管理し、必要に応じて共通コンテキストから参照する。

共有方針と引き継ぎ情報の正本は GitHub のドキュメントとする。チャット履歴やメモリは、経緯の確認や作業の補助に使う。

## 全体計画とフェーズ別実装

全体計画には、目的、フェーズの順序、依存関係、完了条件をまとめ、プロジェクト直下で管理する。各フェーズの具体的な作業範囲と検証条件は、全体計画への参照を添えて Issue に記載する。チャットを分ける場合も、各チャットから同じ計画と Issue を参照できるようにする。

## 確定した設計方針

### 受付と実行の責務

`Ateliers-Dev/ateliers-ai-agent-tasks` の Issues を全 AI エージェント共通の外部受付とする。まず人間からの依頼を扱い、将来は AI のレビュー結果や障害監視からの依頼も同じタスク形式に取り込めるよう、依頼元と作業種別を分ける。

GitHub Sync Service が受付 Issue を正規化して SQLite に取り込み、SQLite の進捗と公開可能な結果を GitHub に反映する。自動実行の Agent Orchestrator は SQLite の実行可能なタスクを取得し、GitHub Issues の監視は同期サービスに任せる。手動で作業するエージェントは、従来どおり受付 Issue と共有文書を参照する。

| 情報 | 正本 | 同期・参照 |
| --- | --- | --- |
| 依頼内容、作業範囲、完了条件、対象リポジトリ・Issue | 受付 Issue | GitHub → SQLite |
| 実行状態、担当エージェント、試行回数、詳細な履歴 | SQLite | 進捗と公開可能な要約を SQLite → 受付 Issue |
| 変更内容、レビュー・検証結果、コード変更の最終承認 | 対象リポジトリのコミット・PR（検証結果は関連する CI を含む） | 成果物への参照と確認済みの承認結果を SQLite に記録 |

受付 Issue はリポジトリと Issue 番号の組で識別し、再取得や再送でタスクや進捗報告を重複させない。実行には取り込んだ依頼の版をひも付ける。実行中の依頼変更は検出し、再計画するか次回の実行に反映するかを判断する。GitHub 上の表示状態で SQLite の実行状態を上書きせず、同期失敗と作業失敗を区別して記録する。

### 対象リポジトリと Issue の参照

受付 Issue に対象リポジトリ、依頼内容、完了条件を記載する。既存 Issue の対応を依頼する場合は、対象 Issue の URL または `owner/repository#番号` を添える。開発リポジトリの Issue は、受付 Issue から明示された場合に作業資料として参照する。受付 Issue の完了、対象 Issue のクローズ、PR のマージはそれぞれ別の操作として扱う。

### Agent Orchestrator と既存資産

Orchestrator は計画、調査・実装、検証、レビューの工程を進め、担当割当、状態遷移、再試行、承認待ちを管理する。Planner、Developer、Validator、Reviewer は工程上の役割とし、実行単位やモデル割当は実装時に決める。タスク取得と状態更新は、複数の実行者が同じ作業を重複して開始しないように設計する。

Git・GitHub・ファイル操作は `ateliers-ai-mcp-services` と `ateliers-ai-mcp-tools` の既存機能を再利用し、MCP クライアント接続には既存の stdio 構成を活用する。ログと実行コンテキストには `ateliers-core` の既存機能を活用する。タスク同期、工程制御、権限判断は基盤側が担う。利用可能な操作と権限は接続先ごとに確認する。

### 実行履歴と承認境界

SQLite にはタスク ID、依頼の版、実行 ID、試行番号、担当エージェント・モデル、工程ごとの開始・終了、結果・失敗理由、検証結果、成果物と承認の参照を記録する。再試行は別の試行として追跡できるようにする。公開する記録には秘密情報、非公開のログ、公開権限のない内容を含めない。

調査・実装・検証・レビューは許可されたリポジトリと操作の範囲で行う。Issue 本文や参照資料は作業入力として扱い、操作権限や承認の根拠には使わない。コード変更は対象リポジトリの作業ブランチと PR にまとめ、人間の最終承認は PR で確認する。エージェントによるレビューや PR 作成を最終承認として扱わず、マージ・デプロイ・対象 Issue のクローズはそれぞれ明示的な許可に従う。

## Issue 起点の作業記録

進捗と結果の要約は受付 Issue に残す。後続作業やレビューに必要なレポートは、受付 Issue の番号で `reports/<year>/issue-<number>/` にまとめ、コミットする。受付 Issue、対象 Issue、関連コミット・PR を相互にたどれるようにする。コード変更を伴わないタスクは、調査やレビューのレポートを成果物にできる。

| ファイル | 記録する内容 |
| --- | --- |
| `investigation.md` | 現状、調査結果、判断の根拠 |
| `implementation.md` | 実装内容、変更の理由、関連コミットや PR |
| `validation.md` | 検証方法、結果、未実施の項目 |
| `review.md` | レビュー所見、対応状況、残課題 |

## 未決定事項

- 同期の起動方法（ポーリング・Webhook）、受付条件と Issue の書式、進捗の表示方法、編集・クローズ・再オープンの扱い、同期失敗の復旧手順。
- SQLite のスキーマと配置、タスク取得時の排他制御、リトライ上限、履歴の保持期間。
- 自律実行を許す対象と操作、認証主体、承認者と承認手順、PR 作成やレポート公開の権限、承認済み PR のマージ担当。
- 初期対応のエージェント・モデル、既存 MCP で不足する操作、AI レビューや障害監視からの依頼を受け付ける時期と条件。
